================================================================================
  1. PROJECT OVERVIEW
================================================================================

UniLost is a web-based Lost & Found management platform designed specifically
for university campuses. When a student loses an item (wallet, ID card,
earphones, bag, etc.) on campus, they can report it on UniLost. Similarly,
if someone finds an item, they post it as a "Found Item". The platform then
uses an AI matching engine to automatically compare lost and found reports
and rank the best potential matches.

The key innovation is the AI engine — it combines:
  - Perceptual image hashing (pHash) using DCT
  - Jaccard text similarity on descriptions/names
  - Category exact matching
  - Location overlap scoring
  - Color and brand bonus scoring

This replaces the manual bulletin board system (WhatsApp groups, notice boards)
that most colleges still rely on, and makes the recovery process faster and
more reliable.

================================================================================
  2. PROBLEM STATEMENT
================================================================================

Students at universities frequently lose personal belongings on campus.
The current methods of recovering lost items are:

  - Posting in WhatsApp groups (noisy, hard to search, no structure)
  - Going to the admin office (slow, limited hours, items get misplaced)
  - Pinning notices on physical boards (ineffective, no images)

These methods have several problems:
  - No image comparison — a text description of "black bag" matches hundreds
  - No automated notifications — the owner may never see the found post
  - No structured data — impossible to filter by category, date, location
  - No direct messaging between finder and owner
  - No accountability — no claim verification process

UniLost solves all of these with a structured, AI-powered digital platform.

  8. AI MATCHING ENGINE (CORE INNOVATION)
================================================================================

  The AI matching engine is the most technically advanced part of UniLost.
  It uses a composite scoring system combining 4 signals.

  ── SIGNAL 1: IMAGE SIMILARITY (pHash) ──────────────────────────────────────

  Algorithm: Perceptual Hashing (pHash) with DCT
  Implemented in: ImageMatchingService.java

  Steps:
  1. Load both images from disk using Java ImageIO
  2. Resize each image to 32×32 pixels (grayscale)
  3. Apply 2D Discrete Cosine Transform (DCT) to the 32×32 grid
  4. Extract the top-left 8×8 block (64 DCT coefficients — low frequency info)
  5. Compute the mean of those 64 values
  6. Build a 64-bit hash: bit[i] = 1 if DCT[i] >= mean, else 0
  7. Compare two hashes using Hamming Distance:
       similarity = (1 - hammingDistance / 64) × 100

  Why pHash?
  - Tolerant to resizing, compression, slight rotation
  - Color-blind (grayscale) — structure matters, not exact colors
  - Pure Java — no OpenCV or external libraries needed
  - Fast — compares hundreds of pairs in milliseconds

  Score interpretation:
    ≥ 90 → Very likely the same item
    75-89 → Similar appearance
    50-74 → Possibly similar
    < 50  → Visually different

  ── SIGNAL 2: TEXT SIMILARITY (Jaccard) ──────────────────────────────────────

  Algorithm: Jaccard Similarity on tokenized text

  Process:
  1. Tokenize item name, description, brand into word sets
  2. Remove stop words (a, the, is, in, on, with, and, etc.)
  3. Compute: |intersection| / |union| × 100

  Weighted:
    Item name      → 50% of text score
    Description    → 30% of text score
    Brand (exact)  → 20% of text score

  ── SIGNAL 3: CATEGORY SIMILARITY ───────────────────────────────────────────

  Exact string match on category (e.g. "Electronics" == "Electronics" → 100%)
  Categories: Electronics, ID Cards, Books, Bags, Keys, Clothing,
              Accessories, Documents, Water Bottles, Other

  ── SIGNAL 4: LOCATION SIMILARITY ───────────────────────────────────────────

  1. Exact match → 100 points
  2. One contains the other → 70 points
     (e.g. "Library 2nd Floor" contains "Library")
  3. Word overlap (Jaccard on location tokens) → proportional score

  ── BONUS: COLOR + BRAND ─────────────────────────────────────────────────────

  Color exact match → +5 to +10 bonus points
  Color partial ("dark blue" vs "blue") → +2.5 to +5 bonus points
  Brand exact match → +5 bonus points

  ── COMPOSITE SCORE ─────────────────────────────────────────────────────────

  When BOTH items have images:
    Final Score = (Image × 60%) + (Category × 20%) + (Text × 10%)
                + (Location × 10%) + color/brand bonus

  When ONE or BOTH items have NO image:
    Final Score = (Category × 40%) + (Text × 35%) + (Location × 25%)
                + larger color/brand bonus

  This adaptive weighting ensures text-only matches still work well
  when users don't upload photos.

  ── THRESHOLDS ───────────────────────────────────────────────────────────────

  Save to DB threshold    : ≥ 25%   (generous, user decides relevance)
  Notification threshold  : ≥ 55%   (only notify for meaningful matches)
  Confidence labels:
    ≥ 90% → "Very High Match"
    ≥ 75% → "High Match"
    ≥ 55% → "Possible Match"
    < 55% → "Low Match"

  ── WHEN MATCHING RUNS ───────────────────────────────────────────────────────

  Automatically:
  - When a new lost item is reported → matched against all found items
  - When a new found item is reported → matched against all lost items

  Manually:
  - Admin "Generate Matches" button → scans all lost × found pairs
  - User "Generate Matches" button on the Matches page

  11. SECURITY & AUTHENTICATION
================================================================================

  Password Security:
  - All passwords hashed with SHA-256 before storage
  - No plain text passwords ever stored or logged
  - Implemented in PasswordUtil.java

  Session Management:
  - User session stored in browser localStorage as JSON
  - No server-side sessions (stateless REST API)
  - Client sends user ID in API calls for user-specific data
  - Note: this is appropriate for a college project, not production grade

  Route Protection:
  - requireLogin() in common.js redirects to login if no session
  - requireAdmin() checks role === "ADMIN" before admin access
  - Backend re-validates role on sensitive admin endpoints

  Input Validation:
  - Email format validated with regex (both frontend + backend)
  - Password minimum 6 characters enforced
  - All text inputs sanitized with escHtml() before rendering
  - File upload restricted to JPG/PNG/WebP, max 5MB

  Reset Token Security:
  - Password reset uses a time-limited token (Base64 of email + timestamp)
  - Token expires after 15 minutes
  - Email must match token to reset password

    mvn clean spring-boot:run

    http://localhost:8080

  --------------------------------
  1. Register a normal account
  2. Run this SQL to promote it to admin:
     UPDATE users SET role = 'ADMIN' WHERE email = 'your@email.com';
  3. Log in using the Admin tab on the login page

  Note: The /uploads/ folder is created automatically when the first
  image is uploaded. Uploaded images are stored there.

================================================================================
  14. KNOWN LIMITATIONS
================================================================================

  [1] No real email verification — registration is instant (no OTP)
      This was removed to simplify setup. In production, email verification
      would be required.

  [2] Stateless auth via localStorage — not suitable for production.
      A proper app would use JWT tokens or server-side sessions with cookies.

  [3] No HTTPS — runs on plain HTTP. Production deployment requires SSL.

  [4] pHash is approximate — two different items that look similar structurally
      might score high (e.g. two black wallets). Human judgment is still needed.

  [5] No WebSocket — messages use polling (API calls every few seconds).
      True real-time messaging would require WebSocket/SSE.

  [6] Images stored on local disk — in production, cloud storage (S3, etc.)
      would be used. Uploaded files are lost if server is moved.

  [7] No rate limiting on API endpoints — a production API needs rate limiting
      to prevent abuse.

  [8] Admin sidebar hidden on mobile — admin dashboard requires larger screens.
      No responsive admin navigation currently.

  [9] SHA-256 for passwords — while better than plain text, bcrypt or Argon2
      is the industry standard for password hashing.
